# 질문 하나 따라가기

[POC 소개](../README.md) → 질문 처리 흐름 → [구조와 역할](./ARCHITECTURE.md)

> 미국 여자 고객이 구매한 야구용품의 매상 합계를 조회해줘.

이 질문은 상품 목록이 아니라 조건에 해당하는 판매금액 전체의 합계를 요구한다. 시스템이 이 의미를 어떻게 데이터와 연결하고 실행 결과로 답하는지 순서대로 살펴본다. 아래 JSON과 문장은 이해를 위한 발췌 예시이며 실제 모델의 프롬프트·응답 전문은 아니다.

## 1. 원문과 요청을 먼저 저장한다

사용자 질문이 들어오면 모델을 호출하기 전에 요청 ID를 만들고 원문을 저장한다. 사용자가 지정한 대화 ID와 turn ID도 함께 보관한다. 같은 요청이 네트워크 문제로 다시 들어왔는지, 같은 문장으로 새로 조회하려는 것인지 구분하기 위해서다.

이후 각 Worker는 요청 ID를 전달받아 같은 저장 문맥을 확인한다. 앞 Worker가 무엇을 했는지 대화 내용을 추측해 이어 가지 않는다.

## 2. 표현을 실제 값과 업무 의미에 연결한다

표준화 Worker는 기존 사전과 질문 용어 정보를 읽는다. 국가 “미국”은 United States of America, 성별 “여자”는 F, 상품분류 “야구용품”은 Baseball에 연결한다. “매상”은 조건값이 아니라 매출액이라는 지표의 표현이다.

이때 표준화는 “미국”을 영어로 번역하는 데서 끝나지 않는다. 실제 데이터에 사용하는 값과 연결되어야 SQL 조건에 쓸 수 있다. 상품을 지칭하는 표현이면 상품 ID까지 해소하고, 후보가 여러 개이면 실제 후보를 사용자에게 묻는다.

## 3. 무엇을 조회할지 정한다

조회 Worker는 표준화 문맥과 메타정보를 이용해 요구사항을 구성한다. 이 예시에서는 판매 데이터셋, 국가·성별·분류 필터, 매출액 SUM, 그룹 기준 없음이 핵심이다.

~~~json
{
  "dataset_key": "sales",
  "action": "RUNSQL",
  "filters": [
    {"field": "country", "operator": "=", "value": "United States of America"},
    {"field": "gender", "operator": "=", "value": "F"},
    {"field": "category", "operator": "=", "value": "Baseball"}
  ],
  "group_keys": [],
  "required_outputs": ["revenue_sum"]
}
~~~

“야구용품”을 언급했다는 이유로 상품별 GROUP BY를 추가하면 질문과 다른 결과가 된다. 필터와 집계 기준을 구분하고, 선택한 데이터셋에서 해당 필드를 사용할 수 있는지 확인한다.

## 4. SQL을 만들고 실행 전에 검토한다

조회 Worker가 SQL을 생성하면 검토 Worker가 소스·조건·출력·집계 기준을 질문과 대조한다. 허용된 SELECT인지 파싱하고, 컬럼 구조와 메타정보 제약도 확인한다. 모델의 의미 검토와 코드 검사를 함께 사용하며, 임의 SQL의 정확성을 완전히 증명하는 것은 아니다.

다음은 같은 조건의 답을 대조하기 위한 기준 SQL이다. 모델이 반드시 이 문장을 문자 그대로 생성한다는 뜻은 아니다.

~~~sql
SELECT SUM(s.amount_sold) AS revenue_sum
  FROM sales s
  JOIN products p ON p.prod_id = s.prod_id
  JOIN customers c ON c.cust_id = s.cust_id
  JOIN countries n ON n.country_id = c.country_id
 WHERE n.country_name = 'United States of America'
   AND c.cust_gender = 'F'
   AND p.prod_category = 'Baseball';
~~~

승인되면 요청 버전, SQL 버전과 SQL 원문 전체를 저장한다. 승인은 “이 요청의 이 SQL”에 대한 승인이다. 이후 조건이나 SQL이 바뀌면 기존 승인을 그대로 사용할 수 없다.

## 5. 승인된 SQL을 그대로 실행한다

조회 Worker가 실행 도구를 호출하면 DB 프로그램이 현재 SQL과 승인 SQL 전체를 비교한다. 일치하고 상태·버전·실행 허용 조건이 맞을 때만 저장한 SQL을 DBMS_SQL로 실행한다. 실행 단계에서 모델에 새 SQL을 만들어 달라고 요청하지 않는다.

행 잠금과 저장 상태 검사로 경쟁 호출을 제어하고, 실행한 SQL 및 원시 결과를 기록한다. SQL만 작성하거나 설명해 달라는 질문은 이 실행 단계로 들어가지 않아야 한다.

## 6. 결과를 확인하고 답변한다

검토 Worker가 실행 결과의 컬럼과 형태 등을 확인한다. 조회 Worker는 검토된 수치와 표시 규칙으로 보고서를 만든다. 마지막으로 공개 진입점이 승인·실행 SQL, 검토 결과, 보고서 버전을 확인해 사용자에게 반환한다.

11월 20일 동일 조건의 집계 기준값은 **6,063,776.96**이었다. 보고서는 질문의 “매상”이라는 표현을 유지해 이 수치를 보여준다. SH에는 통화 컬럼이 없으므로 USD 표시는 POC의 가정이며 환율 변환을 의미하지 않는다. 이번 문서의 “미국” 표현으로 모델 추론을 다시 실행한 결과는 아니므로 직접 시험에서 원시 행과 기준 SQL을 대조한다.

## 상품 후보가 여러 개라면

“Team shirt”처럼 이름만으로 상품 하나를 정할 수 없으면 SQL을 만들기 전에 멈추고 실제 상품 ID와 명칭을 보여준다. 사용자가 고른 ID가 반환 후보인지 코드에서 확인한 뒤 요청 버전을 올리고 이어 간다. 이전 승인과 결과는 무효화한다.

현재 Human Worker 대기가 상위 Team의 대기 상태로 반영되지 않는 문제가 있으므로, 완료 여부는 DB에 저장된 사용자 확인 상태를 기준으로 판단한다. 실제 재개 호출과 확인 방법은 [실행 가이드](./RUNBOOK.md)에 있다.
